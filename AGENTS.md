# AGENTS.md --- PromptFlow

> Главный документ с контекстом проекта и правилами работы для OpenAI
> Codex. Перед выполнением задачи прочитай этот файл целиком. Если в
> репозитории есть дополнительные `AGENTS.md`, соблюдай также
> инструкции, относящиеся к изменяемым каталогам.

## 1. Назначение проекта

**PromptFlow** --- веб-приложение на Flask для организации производства
AI-контента: видеороликов, изображений, анимации и других визуальных
материалов.

Приложение помогает автору пройти путь от идеи до структурированного
плана производства: - создать контент-проект; - разбить его на сцены; -
хранить библиотеку промптов; - сохранять версии промптов и причины
изменений; - оценивать результаты разных версий; - экспортировать план
проекта в Markdown или JSON; - просматривать базовую статистику по
проектам и промптам.

Это инструмент **планирования и организации рабочего процесса**, а не
генератор изображений или видео. Приложение не должно зависеть от
конкретного AI-сервиса.

## 2. Главная цель разработки

Создать небольшой, законченный и хорошо документированный Flask-проект,
который: 1. решает понятную практическую задачу; 2. демонстрирует
качественную структуру Python-приложения; 3. показывает работу с базой
данных, миграциями, формами, авторизацией, тестами и Docker; 4. подходит
для публичного GitHub-репозитория и портфолио разработчика; 5. остаётся
понятным для разработчика, который продолжает изучать Python и Flask.

**Приоритет --- надёжный законченный MVP, а не максимальное количество
технологий.**

## 3. Правила работы Codex

Перед изменениями:

1.  Изучи текущую структуру репозитория и существующий код.
2.  Прочитай этот файл и относящиеся к задаче инструкции `AGENTS.md`.
3.  Определи, что уже реализовано, и не создавай дубликаты.
4.  Проверь используемые версии библиотек, конфигурацию и соглашения
    проекта.
5.  Сформулируй короткий план для многошаговой или рискованной задачи.
6.  Делай небольшие, логически завершённые изменения.

Во время работы:

-   Не переписывай весь проект, если задачу можно решить локальным
    изменением.
-   Не удаляй работающую функциональность без необходимости.
-   Не подменяй реальные реализации заглушками без явного согласования.
-   Не добавляй зависимости и архитектурные слои «на будущее», если для
    них нет текущей задачи.
-   Не вводи сложные абстракции, когда достаточно простого и читаемого
    решения.
-   Соблюдай существующий стиль кода и структуру репозитория.
-   Для новых функций добавляй тесты.
-   При изменении схемы БД создавай миграцию, если проект использует
    Flask-Migrate.
-   Не утверждай, что тесты прошли, если ты их не запускал.
-   Если команда не выполнена или тест не прошёл, сообщи об этом прямо.
-   Не скрывай ограничения среды выполнения.
-   Не выполняй `git commit`, `git push`, удаление веток или другие
    необратимые действия без прямого запроса пользователя.
-   Не помещай секреты, реальные пароли, токены или личные данные в код,
    тестовые фикстуры, README или логи.
-   Не меняй зависимости, версии Python или инфраструктуру без
    обоснованной причины.
-   Если требования неоднозначны и решение может повлиять на архитектуру
    или данные, сначала задай один конкретный уточняющий вопрос. В
    остальных случаях выбирай самый простой безопасный вариант и явно
    обозначай допущение.

После изменений:

1.  Запусти подходящие тесты.
2.  Проверь форматирование и линтер, если они настроены.
3.  Проверь `git diff`, чтобы убедиться, что в изменениях нет случайных
    правок и секретов.
4.  В итоговом сообщении перечисли, что сделано, какие проверки запущены
    и что осталось.

## 4. Технологический стек

Предпочтительный стек проекта:

-   Python --- основная логика;
-   Flask --- веб-фреймворк;
-   Flask-SQLAlchemy --- ORM и работа с БД;
-   PostgreSQL --- основная база данных;
-   Flask-Migrate / Alembic --- миграции схемы;
-   Flask-Login --- управление пользовательскими сессиями;
-   Flask-WTF / WTForms --- формы и CSRF-защита;
-   Jinja2 --- серверный рендеринг HTML;
-   Bootstrap 5 --- адаптивный интерфейс;
-   pytest --- тестирование;
-   Ruff --- линтинг и форматирование, если он настроен;
-   Docker и Docker Compose --- воспроизводимый локальный запуск;
-   GitHub Actions --- автоматический запуск проверок.

Не добавляй Celery, Redis, SPA-фреймворк, REST API, платёжные системы
или интеграции с генеративными API только ради списка технологий.
Сначала должна появиться подтверждённая потребность.

Если репозиторий уже содержит согласованный стек или зафиксированные
версии, не меняй их автоматически ради соответствия этому списку.

## 5. Основные функциональные требования

### 5.1. Пользователи и доступ

-   Пользователь может зарегистрироваться, войти и выйти из системы.
-   Пароли хранятся только в виде безопасного хеша, никогда в открытом
    виде.
-   Пользователь видит и изменяет только принадлежащие ему проекты,
    сцены, промпты, версии и оценки.
-   Все запросы к пользовательским данным должны учитывать текущего
    пользователя.
-   Нельзя полагаться только на скрытие ссылок в интерфейсе: доступ
    проверяется на сервере.
-   При попытке открыть чужой объект приложение не должно раскрывать его
    содержимое.
-   Формы защищены от CSRF, где это применимо.
-   Валидация выполняется на сервере, даже если есть клиентские
    ограничения.

### 5.2. Проекты

Проект хранит как минимум: - владельца; - название; - описание или
исходную идею; - визуальный стиль; - формат контента, например
вертикальное или горизонтальное видео; - дату создания и дату последнего
изменения.

Пользователь может создавать, просматривать, редактировать и удалять
собственные проекты. Перед удалением связанных данных учитывай выбранную
стратегию каскадного удаления и обеспечивай предсказуемое поведение.

### 5.3. Сцены

Сцена относится к одному проекту и хранит: - порядковый номер; -
название; - описание действия или кадра; - предполагаемую
длительность; - статус производства, например `planned`, `in_progress`,
`done`.

Пользователь может добавлять, редактировать, удалять и упорядочивать
сцены. Проверяй, что сцена действительно принадлежит проекту текущего
пользователя. Не допускай дублирующегося или некорректного порядка сцен,
если операция требует уникального порядка.

### 5.4. Библиотека промптов

Промпт может содержать: - название; - назначение или тип генерации; -
AI-сервис, для которого он предназначен, если это известно; - теги; -
дату создания и дату обновления.

В текстах промптов могут быть: - основной prompt; - negative prompt; -
параметры камеры; - освещение; - визуальный стиль; - формат кадра; -
дополнительные заметки.

Названия сервисов --- обычные данные. Не привязывай бизнес-логику к
конкретному поставщику AI.

### 5.5. Версии промптов

-   Изменение текста промпта создаёт новую версию, а не уничтожает
    предыдущую.
-   Версия хранит текст промпта, negative prompt, номер версии, дату
    создания и примечание об изменении.
-   Сохранённая версия считается неизменяемой в обычном рабочем
    процессе.
-   Новая версия получает последовательный номер в пределах
    соответствующего промпта.
-   Проверяй принадлежность промпта текущему пользователю до чтения или
    изменения версий.
-   Обеспечь сортировку версий по номеру или времени создания.

### 5.6. Оценки результатов

Пользователь может оценить версию промпта по шкале от 1 до 5 и оставить
комментарий о результате.

-   Проверяй диапазон оценки на сервере.
-   Не позволяй оценивать версии чужих промптов.
-   Если пользовательская модель предполагает одну оценку на версию от
    одного пользователя, обеспечь это ограничение на уровне приложения
    и, где возможно, БД.
-   Статистика должна корректно работать и при отсутствии оценок.

### 5.7. Поиск и фильтрация

Добавляй поиск и фильтры по мере реализации MVP: - название промпта; -
текст или назначение; - теги; - тип генерации или сервис.

Поиск должен быть ограничен данными текущего пользователя. Не загружай
все записи в память без необходимости.

### 5.8. Экспорт

Поддерживаемые форматы: - **Markdown** --- читаемый производственный
документ со сведениями о проекте, сценами и связанными промптами; -
**JSON** --- структурированные данные для повторного использования.

Требования: - экспортируется только доступный текущему пользователю
проект; - данные сериализуются безопасно и предсказуемо; - формат
экспорта документирован; - пустые поля и отсутствие сцен обрабатываются
без ошибок; - экспорт не должен содержать секреты или данные других
пользователей.

### 5.9. Главная панель и аналитика

Предусмотри простую панель с полезными показателями: - количество
проектов; - количество сцен; - количество промптов и версий; - средняя
оценка, если оценки существуют; - наиболее высоко оценённые версии.

Статистика считается по данным текущего пользователя. Не усложняй
аналитику без конкретной потребности.

## 6. Предлагаемая архитектура

Используй Application Factory и Blueprints, если это соответствует
текущей структуре приложения.

Ожидаемое разделение ответственности:

-   **routes / blueprints** --- HTTP-маршруты, проверка доступа,
    связывание формы и сервисов;
-   **forms** --- поля форм и валидация ввода;
-   **models** --- сущности SQLAlchemy и связи между ними;
-   **services** --- логика экспорта, версионирования и аналитики, когда
    вынос упрощает тестирование;
-   **templates** --- HTML-шаблоны Jinja2;
-   **static** --- CSS, JavaScript и статические ресурсы;
-   **tests** --- тесты моделей, маршрутов, авторизации и бизнес-логики.

Не создавай сервис или отдельный модуль для каждой тривиальной операции.
Архитектура должна помогать читать и тестировать код, а не увеличивать
число файлов ради самого разделения.

## 8. Модель данных и связи

Ожидаемые сущности:

-   `User`: учётная запись и владелец данных.
-   `Project`: проект пользователя.
-   `Scene`: сцена конкретного проекта.
-   `Prompt`: запись библиотеки промптов.
-   `PromptVersion`: неизменяемый снимок определённой версии промпта.
-   `PromptRating`: оценка версии и комментарий.

Ожидаемые связи: - один пользователь владеет многими проектами; - один
проект содержит много сцен; - пользователь владеет своими промптами; -
один промпт содержит много версий; - одна версия может иметь несколько
оценок в соответствии с принятой моделью оценивания.

Уточняй внешние ключи, ограничения уникальности, индексы и правила
удаления исходя из реальных запросов и требований. Не добавляй поля,
которых никто не использует.

## 9. Безопасность и обработка ошибок

Обязательно учитывай:

-   хеширование паролей средствами проверенной библиотеки или Werkzeug;
-   CSRF-защиту для форм;
-   проверку владельца объекта при каждом чтении и изменении;
-   валидацию длины и формата пользовательского ввода;
-   безопасный вывод пользовательского текста через механизмы Jinja2;
-   защиту от SQL-инъекций через ORM и параметризованные запросы;
-   секретный ключ из переменной окружения;
-   отсутствие реальных секретов в репозитории;
-   понятные страницы или ответы для ошибок 403/404/500;
-   недопустимость показа traceback и конфигурационных секретов
    пользователю в production;
-   ограничения на экспортируемые данные и корректные имена скачиваемых
    файлов.

Не добавляй собственную криптографию. Не отключай проверку CSRF или
авторизацию ради упрощения тестов.

## 10. Тестирование

Используй pytest. Тесты должны проверять поведение, а не только факт
успешного импорта.

Минимальный набор:

### Авторизация

-   регистрация успешна;
-   повторная регистрация с тем же email обрабатывается корректно;
-   корректный вход и выход;
-   неверный пароль не даёт войти;
-   приватные страницы недоступны анонимному пользователю.

### Изоляция пользователей

-   пользователь A не может открыть проект пользователя B;
-   пользователь A не может редактировать или удалить сцену пользователя
    B;
-   нельзя читать или изменять чужие промпты и версии;
-   экспорт не включает чужие данные.

### Проекты и сцены

-   создание, изменение и удаление проекта;
-   создание и изменение сцены;
-   корректность статусов и порядка сцен;
-   обработка отсутствующих или неверных идентификаторов.

### Промпты и версии

-   создание промпта;
-   создание новой версии;
-   старая версия остаётся доступной после создания новой;
-   номера версий корректны;
-   оценка вне диапазона 1--5 отклоняется;
-   отсутствие оценок не ломает статистику.

### Экспорт

-   корректный JSON;
-   читаемый Markdown;
-   корректная обработка пустого проекта;
-   отсутствие данных другого пользователя.

Используй отдельную тестовую конфигурацию и изолированную тестовую БД.
Тесты не должны удалять или изменять реальные пользовательские данные.
Если PostgreSQL недоступен в тестовой среде, сообщи об этом; не заявляй,
что PostgreSQL-проверки выполнены, если вместо него использовалась
другая БД.

## 11. Конфигурация и запуск

-   Конфигурация должна отделять development, testing и production.
-   Секреты и строки подключения задаются через переменные окружения.
-   Добавь `.env.example` с безопасными примерными значениями и
    пояснениями.
-   Не добавляй настоящий `.env` в Git.
-   Docker Compose должен обеспечивать понятный локальный запуск
    приложения и PostgreSQL.
-   README должен содержать команды создания окружения, установки
    зависимостей, миграций, запуска тестов и старта приложения.
-   Команды в документации должны соответствовать реально реализованной
    конфигурации.
-   Не придумывай команды и не обещай автоматическую настройку, если она
    не реализована.

## 12. Качество кода

-   Следуй PEP 8 и существующим настройкам форматирования.
-   Используй понятные имена функций, переменных и моделей.
-   Предпочитай небольшие функции с одной ответственностью.
-   Добавляй type hints там, где они улучшают ясность, не превращая
    учебный проект в сложную систему типов.
-   Не дублируй бизнес-логику в нескольких маршрутах.
-   Не используй глобальное состояние приложения вместо Flask
    application context и extensions.
-   Не перехватывай все исключения без необходимости.
-   Не оставляй отладочный код, временные пароли и неиспользуемые
    зависимости.
-   Комментарии должны объяснять причины и нетривиальные решения, а не
    пересказывать каждую строку.

## 13. Этапы разработки

Выполняй работу небольшими этапами. Не реализуй всё за один огромный
коммит или изменение.

### Этап 1. Основа

-   проверить окружение и структуру;
-   создать Flask application factory;
-   подключить конфигурацию и расширения;
-   настроить базовую страницу и `/health`;

## 14. Критерии готовности MVP

MVP считается готовым, когда новый разработчик может по README:

1.  получить проект и настроить окружение;
2.  запустить приложение и базу данных;
3.  зарегистрировать пользователя;
4.  создать проект и несколько сцен;
5.  создать промпт и сохранить несколько его версий;
6.  оценить версии и посмотреть результаты;
7.  экспортировать проект в Markdown и JSON;
8.  убедиться, что пользователь не имеет доступа к чужим данным;
9.  запустить тесты и получить понятный результат.

Также должны быть: - миграции БД; - `.env.example`; - отсутствие
секретов в Git; - документация по запуску; - понятные инструкции по
тестам; - проверенная базовая обработка ошибок.

## 15. Документация и GitHub-портфолио

README должен объяснять: - какую проблему решает PromptFlow; - для кого
предназначен проект; - основные функции; - используемый стек; -
архитектуру и основные модели; - требования к окружению; - установку и
запуск; - миграции; - запуск тестов; - примеры экспорта; - известные
ограничения; - скриншоты интерфейса, когда он будет готов.

Не заявляй в README или резюме о функциях, которые фактически не
реализованы. Не добавляй фиктивные бейджи успешных тестов или CI.

## 16. Как выполнять запросы пользователя

Пользователь изучает Python и веб-разработку, поэтому решения должны
быть понятными и пригодными для обучения.

Для каждой существенной задачи: 1. кратко объясни, что нужно сделать и
зачем; 2. перечисли файлы, которые планируешь изменить; 3. внеси
минимально достаточные изменения; 4. запусти относящиеся к задаче
проверки; 5. объясни результат простым русским языком; 6. приведи точные
команды для действий, которые пользователь должен выполнить вручную.

Не перескакивай на дополнительные технологии или сложные темы, не
необходимые для текущего этапа. Если есть несколько решений, по
умолчанию выбирай самое простое поддерживаемое и объясняй компромисс.

В итоговом сообщении используй формат:

-   **Сделано:** краткий список изменений.
-   **Проверки:** какие команды реально запущены и каков результат.
-   **Важно:** ограничения, допущения или нерешённые проблемы.
-   **Следующий шаг:** одно наиболее логичное продолжение.

## 17. Первое действие Codex в новом репозитории

Если пользователь просит начать работу над проектом, сначала:

1.  проверь, что текущий репозиторий действительно относится к
    PromptFlow;
2.  изучи файлы, историю и существующие зависимости;
3.  сравни реальное состояние с этим документом;
4.  сообщи краткий план и список отсутствующих компонентов;
5.  реализуй только первый согласованный небольшой этап.

Если репозиторий имеет другое название или уже содержит иной проект,
**не переименовывай и не заменяй его автоматически**. Сообщи о
несоответствии и уточни намерение пользователя.
